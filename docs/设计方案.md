# Tao 第一阶段设计方案

本文档记录 Tao 桌面应用与 Pi 内核的第一阶段设计。

顶层边界和长期架构约束见 [顶层设计.md](./顶层设计.md)。总体路线见 [总纲与路线图.md](./总纲与路线图.md)，Pi 能力核对见 [Pi能力清单与映射.md](./Pi能力清单与映射.md)。本方案必须遵守“Tao 是产品、Pi 是引擎”的原则。

## 目标

验证 React 前端、Tauri command、Pi CLI 和前端消息展示的完整链路，并提供可测试的基础对话与模型配置界面。

## 总体架构

```text
Tao React 前端
  -> Tauri command
  -> Rust PiAdapter
  -> 单一 Tao Node Runtime 长驻进程
  -> 多个独立 Pi AgentSession
  -> Tauri event 流式返回思考和答案
```

Pi release source 会复制到 `vendor/pi`，运行时只使用 Tao 项目内的副本。用户数据不写入源码目录，目标是统一放入用户根目录下的 `.tao`。

## 项目结构

- `src/`：React + TypeScript 界面。
- `src-tauri/src/`：Rust command、Pi 进程桥接和运行时存储。
- `vendor/pi/`：固定版本的 Pi release source。
- `docs/`：Tao 的顶层设计、阶段方案和开发记录。
- Tauri 构建缓存和运行时用户数据不作为核心源码。

## 会话和记忆

每个 Tao 对话对应一个独立 Pi `AgentSessionRuntime`，所有会话由一个 Tao Node Runtime 宿主托管。Node、Pi SDK、模型目录和认证配置在应用生命周期内只初始化一次；新建会话只创建 Session 对象，切换会话只改变前端显示目标，不重启 Node/Pi 进程。Pi 继续负责历史上下文、记忆压缩和上下文管理。Pi session JSONL 是对话内容的事实源。模型、Base URL、API 协议、思考模式或 key 改变时，Tao 统一重启宿主并按新配置恢复需要使用的 session。

当前版本的 `conversation.json` 仍保存一份消息投影，便于第一阶段 UI 快速加载；这是过渡设计，后续应改为只保存 Tao 会话元数据，并通过 Pi RPC `get_messages` 或 `get_entries` 读取消息。

## 第一阶段功能

- 中文 Codex 风格的左侧对话栏和中央消息区。
- 新建对话、切换对话、消息发送和错误显示。
- Provider、Model、Base URL 和 API key 全局配置。
- OpenAI-compatible Base URL、API 协议选择、连接测试和远程模型列表获取。
- Pi RPC 非交互调用，思考和回答通过 Tauri event 增量返回。
- 生成中的思考区可以折叠；正文开始时自动收起，完成后用持久化消息替换临时流。
- 生成中可以停止、用 `steer` 立即追加调整，或用 `follow_up` 在当前回答后继续。
- 多个会话可以同时生成；每个会话独立显示启动、生成、停止和错误状态。
- 模型设置中提供模型和思考模式选择，使用 Pi RPC/原生 `defaultThinkingLevel` 配置。
- 顶部运行信息抽屉显示当前 session、进程状态、模型、思考模式、当前会话工作区和排队消息。
- 历史会话支持删除和置顶；置顶是 Tao 产品元数据，不改变 Pi session 内容。
- 对话元数据和界面消息统一保存在 `.tao`；Pi session 作为上下文和消息事实来源。首次启动会把旧 Tauri App Data 中的 Tao 数据复制到 `.tao`，并在旧目录写入迁移完成标记。

第一阶段暂不复刻 Pi TUI、工具原始日志、复杂会话树和 OAuth 登录界面。工具调用显示一条由 Pi 事件归约出的当前状态，并可展开查看安全的执行摘要。

中转站配置通过标准 `GET <Base URL>/models` 验证 key 并获取模型。保存后，Tao 按 Pi 原生格式分别写入 `.tao/models.json`、`.tao/auth.json` 和 `.tao/settings.json`；API key 不进入 Tao 会话或前端持久状态，已保存的 key 可以直接用于后续连接测试。Pi session 统一放在 `.tao/sessions`，不同 Tao 对话使用独立 session，前端生成状态也按 conversation ID 隔离。

## 工作区体验

工作区选择属于会话上下文，不属于全局 Tao Home。顶部显示当前工作区名称和完整路径，输入区左下角提供紧凑的目录入口；选择后，该会话的 Pi Session 使用所选目录作为 `cwd`。工作区名称只影响界面显示，不会改动物理目录。左侧导航按 `workspacePath` 的规范化目录分组，行为与项目型 Agent 客户端一致。

新建会话通过后端传入当前活动会话的工作区并持久化，默认加入当前项目；用户仍可在任意空闲会话中重新选择目录。未选择工作区时，开发构建使用仓库根目录，发布构建使用当前 Windows 用户主目录。`.tao` 只保存会话和配置，不作为工作区，也不限制 Pi 读取用户明确选择的外部目录。

Rust 桥接层只维护一个 Runtime stdin/stdout，并通过请求 ID 和 conversation ID 多路复用。Node 宿主把控制命令路由到目标 AgentSession：

```text
停止按钮      -> Tauri abort_generation -> Pi AgentSession.abort
立即调整      -> Tauri queue_message     -> Pi AgentSession.steer
回答后继续    -> Tauri queue_message     -> Pi AgentSession.followUp
队列/轮次事件 <- Pi AgentSession         -> Tao runtime event
```

`message_end` 仍是持久化消息的依据。被中止的 assistant 消息保存为“已停止”；追加产生的 user/assistant 消息按 Pi 的事件顺序写入当前 Tao 投影，最终由完整 Conversation 替换前端临时流，避免重复显示。

应用启动读取历史时，会用对应 `.tao/sessions/<conversationId>.jsonl` 对 `conversation.json` 做一次轻量对账。若 Pi 已经记录了 `assistant / aborted` 或 `assistant / error` 而 Tao 投影缺失，则补回“已停止”或错误消息；空的 aborted 轮次也会显示可继续提示，不会让历史会话卡在不可恢复状态。

## 并发和预热

前端不再使用单一的全局发送锁，而是按 `conversationId` 保存运行状态。Node Runtime 按会话维护独立 `AgentSessionRuntime`，控制命令只发送到目标 Session。切换会话只改变显示目标，不会暂停其他会话。

预热流程如下：

```text
Tao 启动
  -> 后台启动唯一 Node Runtime
  -> 初始化一次 ModelRuntime 和认证
新建会话
  -> 后台创建 AgentSession（不阻塞输入）
用户发送
  -> Session 未完成时由 Runtime 等待同一创建任务
  -> 直接进入 prompt
```

会话后台创建失败不会阻塞输入或其他会话；发送时会自动重试并返回明确错误。

每轮生成还会通过 `pi-timing` 事件记录首个输出和完整完成耗时，前端显示“首次输出”和“完成”时间，用于区分模型首字延迟与正文生成耗时。

应用启动时不再等待 `get_app_state`、`list_models` 和 Session 预热全部完成。Tao 先加载产品状态并显示主界面，模型目录和 Pi Session 分别后台加载；顶部持续显示启动阶段。耗时数据独立保留在会话运行状态中，因此流式临时消息被持久化 Conversation 替换后仍能在右侧查看。

## 运行信息抽屉

第一阶段先提供运行信息而不是文件浏览器：当前会话工作区、进程状态、当前模型、思考模式、队列和一条最近状态。Pi 使用自身默认内置工具配置，并由 AgentSession 自行决定是否调用；Tao 仅接收工具事件并归约为产品级当前状态与可折叠执行摘要。真实的文件变更摘要和验证摘要仍属于后续能力，工具原始输入、输出与日志不会进入界面。

左侧会话栏和右侧运行栏均可独立显示或收起。右侧使用布局第三栏，不覆盖中间聊天内容。

## Windows 进程策略

开发时可使用 Pi 提供的 `pi-test.bat` 验证入口。Tao 后端优先直接启动 Node 和 `tsx` 入口，并用参数数组传递用户文本，避免把用户输入拼接到 `cmd.exe /C` 字符串中。开发模式从 `vendor/pi` 加载 Pi 源码；Windows x64 发布模式从 Tauri resources 加载内置 Node、Pi 和 Tao Runtime，不依赖目标电脑的 Node.js 或 Tao 源码目录。每个 Conversation 可选择自己的 Agent 工作区，未选择时使用 Runtime fallback cwd。Tao 配置、认证和会话数据始终统一保存在用户目录 `%USERPROFILE%\\.tao`，与 Agent 工作区相互独立。

当前机器的 Cargo 使用项目级 `.cargo/config.toml` 将 crates.io 替换为 rsproxy sparse registry，避免默认 crates.io 索引在本地网络中长期无响应。

## 运行时目录

会话、设置、Pi 配置和日志统一放在 `%USERPROFILE%\.tao`，不写入项目源码目录。首次迁移会复制旧 Tauri App Data 内容但保留原目录作为备份，并通过外部迁移标记避免用户删除 `.tao` 后再次导入旧数据。开发目录中的 `node_modules` 和 `src-tauri/target` 可以重新生成。

## 后续演进

桥接层保持独立，后续可在不改变 Pi session 事实源的前提下加入进程空闲回收、Skill/Agent 管理和工具调用展示。Windows x64 第一版发布链路已经将 Pi、Node Runtime 和 Tao Runtime 制作为 Tauri resources；后续再评估 sidecar、资源裁剪和其他平台构建。
# Tao Runtime 事件层

Pi RPC 的原始事件在 Rust 边界转换为版本化的 `tao-runtime-event`。React 不再直接订阅 `pi-stream` 或 `pi-timing`，只根据 Tao 的 `category/event` 更新消息流、队列、回合状态和耗时。这样后续升级 Pi 或接入工具事件时，只需要调整 Runtime 映射。

## Prompt/Context 工作台

第一版工作台位于左侧“定制 Runtime”，通过 Rust 命令保存 `.tao/runtime/profile.json`。配置包含启用开关、系统提示词模式（追加或替换）、系统提示词和会话附加提示词。启动 Pi RPC 时由 Rust 转换为 Pi 原生 CLI 参数；保存时关闭空闲进程并在当前会话重新预热。生成中禁止保存，避免改变正在运行的上下文。

## 主界面折叠与模型入口

主界面采用“左栏/中央页面/右侧检查器”三栏结构。侧栏关闭后完全退出布局，只在中央页面标题栏左上角或右上角保留无边框面板按钮；打开后通过一条竖线分隔。模型和思考模式位于输入框右下方；Provider、Base URL、API key 等仍在统一设置中管理。思考模式作为 Pi 原生 `--thinking` 参数参与进程配置指纹，选择改变后下一次发送会按新配置重建该会话 Runtime。

左侧主导航固定为“新建会话、定制、历史会话、设置”。“定制”和“设置”不再使用弹窗，而是切换中央主页面，并各自提供二级侧栏。右侧检查器根据当前主页面显示会话运行信息、定制配置摘要或全局设置摘要。

主页面分为：

- 对话：消息、输入框、会话模型和思考模式。
- 定制：概览、系统提示词、上下文、会话策略、Agent、Skill、Extension、权限（后续）。
- 设置：模型与 Provider、外观、语言、数据与会话、Runtime、关于 Tao。

目前系统提示词与模型设置已连接现有后端；其他栏目先建立稳定的信息架构，待 Pi 能力和安全边界确认后逐项接入。
