### 工作过程展示

Tao 的工作过程需要接近 Codex、WorkBuddy 一类产品的阅读体验，但只展示产品级、可读、可追溯的信息：

```text
已工作 12 秒                         >
────────────────────────────────
我先检查项目结构，确认相关文件。

[终端] bash rg STREAM_FLUSH src/App.tsx

我找到流式刷新逻辑了，接着读取 App.tsx。

[读取] src/App.tsx

思考过程
  ...

Tao 的最终回答
```

必须区分以下三类内容：

1. `preamble`
   - 模型面向用户输出的简短工作说明。
   - 例如“我先检查项目结构”“我找到了相关代码，接着确认调用链”。
   - 这是本轮当前最重要的未完成能力。
   - 不得用 Tao 固定文案伪造模型已经观察到的事实。
   - 不得把模型隐藏思考原文直接当作 `preamble`。

2. 工具执行摘要
   - 由 Runtime 根据 Pi 的真实工具事件生成。
   - 例如 `[终端] bash rg ...`、`[读取] src/App.tsx`、`[编辑] src/App.css`。
   - 工具名称保持简洁，参数只允许展示经过脱敏和截断的目标路径或命令预览。
   - 不显示原始参数、文件正文、stdout、完整工具结果或原始事件 JSON。

3. 最终回答
   - 模型的正式回答单独显示。
   - 不能把工具前的 `preamble` 和工具后的最终回答混在同一段正文里。

### 工作面板结构

- 工作面板顶部先显示 `已工作 X 秒` 和展开/收起箭头。
- `已工作 X 秒` 下方只保留一条浅色分界线，不在耗时行上方增加横线。
- 分界线下方是工作过程，正式回答位于工作过程之后。
- 点击耗时行可以展开或收起完整工作过程。
- 生成完成后默认收起；重新打开会保留过程。
- 展开后按照真实时间顺序显示 `preamble`、工具摘要、状态说明和思考内容。
- 思考内容可以单独折叠。
- 当前执行时显示正在进行的步骤，结束后显示完成状态。
- 左侧助手消息不再显示 `Tao` 头像和作者名，保持简洁；最终回答只保留内容和必要操作。
- 工具图标使用简单、小尺寸符号，不使用大型卡片或装饰性图标。
- 模型 `preamble` 使用接近正式回答的正常字号和较深颜色；状态说明和工具记录使用更小、更浅的辅助层级。

## `preamble` 技术边界

### 允许

- 在 Tao Runtime 内订阅 Pi 已有的 assistant message 和工具事件。
- 在 Node Runtime 内部缓存当前 assistant turn 的短文本。
- 根据 assistant turn 最终是否进入工具调用，判断文本属于工作说明还是最终回答。
- 传给 Rust/React 的只有经过截断的 `preamble` 文本和结构化摘要。

### 禁止

- 修改 `vendor/pi`。
- 重写 Pi Agent loop。
- Tao 根据用户问题决定是否使用工具。
- Tao 伪造工具事件或伪造模型已经读取到的内容。
- 将完整隐藏思考、原始工具参数、文件内容、stdout、完整工具结果传给 React。
- 为了展示 `preamble` 而把最终回答延迟到不可接受的程度。

### 已确认的实现方式

当前采用以下方案：

1. Runtime 以 assistant turn 为单位暂存短文本。
2. 如果该 turn 最终进入工具调用，将工具调用前的文本作为 `preamble`。
3. 如果该 turn 最终直接结束回答，将文本作为最终回答。
4. 工具结束后如果模型再次输出说明，重复上述判断。
5. 如果 Pi 的文本块带有明确的阶段标识，优先使用阶段标识；没有时才使用同一 assistant 消息中的真实工具调用边界推断。

该方案需要专门验证流式体验，不能直接把所有 `text_delta` 继续当作最终回答，也不能为了分类而引入新的明显卡顿。

## 验收场景

- [ ] 普通问候：没有工具时不显示虚假的工具过程。
- [ ] 读取文件：显示真实的中文 `preamble`、`read` 工具行和最终回答。
