# Tao 内置 Pi 代码快照与修改规范

最后核对：2026-10-22，对应已发布的 0.2.0。下方 2026-10-19 补丁段保留当批来源与验证范围；后续资源准备、MSI 提取和发布结果见 [0.2.0 验收记录](../验证/2026-10-21-0.2.0发布验收.md)，不将旧段的待发布状态当作当前状态。

## 1. 定位

`vendor/pi` 是 Tao 仓库内的 Pi 固定源码快照，不是 Git submodule，也不跟踪 Pi 上游仓库的最新代码。

使用者克隆 Tao 后直接获得这份 Pi 代码，不需要也不应该另外拉取最新 Pi。

## 2. 基本规则

- `vendor/pi` 作为一个整体跟随 Tao 仓库提交。
- 不得把 `vendor/pi` 改成 Git submodule。
- 不得在文档或脚本中要求使用者安装、更新或维护独立的 Pi 产品目录。
- 后续如果需要修改 Pi，直接修改 `vendor/pi` 下的文件，并随 Tao 代码一起提交。

## 3. 何时可以修改

以下情况可以修改 `vendor/pi`：

- Tao 需要新的集成接口或事件能力。
- 需要修复 Tao 实际运行中暴露的问题。
- 需要裁剪 Pi、AOT 打包或 Windows Runtime 适配。

以下情况不应直接在 `vendor/pi` 中做无跟踪修改：

- 只因个人调试临时改动，事后应当回滚或记录。
- 修改后会导致发布资源无法重新生成或无法回滚。
- 修改逻辑实际上可以放在 Tao 装配层完成。

## 4. 修改后的要求

修改 `vendor/pi` 后，至少需要：

1. 在文档中记录修改目的和范围。
2. 说明是否改变 Pi 的行为、协议或数据格式。
3. 运行 `npm.cmd run check` 或对应的 Tao 验证命令。
4. 需要发布时执行 `npm.cmd run tao:prepare`，确认发布资源可以重新生成。
5. 保留回滚方案，避免把 `vendor/pi` 变成不可追踪的工作副本。

## 5. 许可证和来源

`vendor/pi` 内的原始代码按其自带许可证处理。Tao 自己的新增代码、补丁和集成代码按 Tao 仓库自身的许可规则管理。
