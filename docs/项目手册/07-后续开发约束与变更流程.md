# Tao 后续开发约束与变更流程

这份文档用于防止后续开发破坏现有功能、发布流程和产品边界。

最后核对：2026-10-22，对应 0.2.0。当前开发范围见 [开发 TODO](../开发TODO.md)；历史建议顺序不覆盖后续实现和用户确认。

## 1. 发布流程必须保持可用

涉及以下内容的改动，都必须检查 Debug 和 Release 的资源解析及运行边界，并按影响选择验证：

- `src-tauri/runtime/tao-runtime.mjs`
- `src-tauri/src/runtime.rs`
- `src-tauri/tauri.conf.json`
- `scripts/prepare-tauri-release.mjs`
- Pi 入口、SDK 加载或依赖
- 新增 Node/Rust 依赖
- `vendor/pi` 的资源结构

Runtime 改动通常需要语法、类型与对应回归检查；资源结构或依赖改动还需准备并验证发布资源：

```powershell
node.exe --check src-tauri\runtime\tao-runtime.mjs
npm.cmd run check
npm.cmd run tao:prepare
npm.cmd run tao:verify
```

纯文档维护检查内容一致性、相对引用和 Git 差异，不因此自动重跑模型/沙盒测试或生成安装包。若修改了随包专题文档，另在下一次资源准备/发布验证时核对其副本。

新安装包编译和正式发布前，先汇报具体就绪情况并取得用户确认，再执行 `npm.cmd run tao:release` 及安装验收。上述检查要求不是每次改动都自动打包的授权；已有版本的发布结果不重复执行。

Release 代码不能依赖 Debug 路径。尤其不能把下面这种路径带入发布逻辑：

```text
<Tao 项目根目录>\vendor\pi
<Tao 项目根目录>\src-tauri\runtime
```

发布版必须使用 Tauri resource 目录。

## 2. 依赖变更规则

新增依赖时必须回答：

1. 它属于 Tao 前端、Rust、Runtime 还是 Pi 运行资源；
2. 开发模式如何安装；
3. 发布脚本是否需要复制或下载；
4. 目标电脑是否需要额外安装；
5. 是否增加 MSI 体积；
6. 是否影响 Windows x64；
7. 是否需要更新安装和迁移手册。

不能只把依赖加进 `package.json`，然后假设发布包会自动包含它。

2026-10-22 文档读取依赖属于 Tao Runtime，使用独立的 `src-tauri/runtime/package.json` / 锁文件。开发用 `npm.cmd ci --prefix src-tauri/runtime --ignore-scripts`，setup-dev 已包含此步；不得省略 Windows x64 optional 依赖，PDF.js 的 Node 兼容层需要其中的 canvas 组件。发布准备复制整个 Runtime（含依赖与许可）到 resources/runtime，验证脚本用内置 Node、受限 PATH 和随包解析器实际提取中文 PDF / DOCX，并检查原生组件不依赖外部 VC++ 运行库。安装用户无需额外安装 Office/Python/Node；无配置迁移，现有 read 权限与工具选择继续适用。此批未压缩资源增加约 72.4 MiB，实际 MSI 增量尚未测量。

文档字节沿用所选文件执行后端读取，主机 Worker 只解析获得的字节，限制解析时间、JS 堆、正文 XML 与输出长度；Worker 是生命周期隔离，不是 OS 安全沙盒。解析不执行 PDF JavaScript、宏、外部关系或网络请求。后续增加 OCR、外部资源读取或解析器能力时必须重新检查边界，不能把沙盒附件悄悄改为主机直接打开。

如果依赖属于 Pi 运行时，必须检查 `scripts/prepare-tauri-release.mjs` 是否会把它复制进：

```text
src-tauri/resources/pi/node_modules
```

## 3. `vendor/pi` 的处理规则

当前产品约束是：

- 产品与内核统一称 Tao，保留原始来源和许可证；
- `vendor/pi` 作为 Tao 源码维护，允许按产品需要修改；
- 优先通过 Pi SDK、RPC、ResourceLoader 和 Extension 接入；
- Tao UI、Rust 桥接和 Node Runtime 可以修改。

内核改动必须：

- 记录具体源码位置；
- 记录修改原因和影响范围；
- 记录 Pi 版本；
- 设计补丁或上游同步方式；
- 在发布文档中写清楚；
- 验证资源复制和升级兼容性。

不能把 `vendor/pi` 变成没有版本边界的手工修改目录。

## 4. Runtime 和事件协议规则

React 不应该直接解析 Pi 原始事件。新增事件时：

1. 先在 Node Runtime 归约；
2. 使用稳定的 Tao event category/event；
3. 携带 `conversationId` 和必要的 `requestId`；
4. 只传产品级摘要；
5. 同步更新 Rust `TaoRuntimeEvent`；
6. 同步更新 React 状态处理；
7. 为实时状态和历史恢复分别验证。

不能把原始工具 JSON、完整文件内容、stdout 或 Provider payload 直接放入新事件。

## 5. 会话和并发规则

新增发送、重试、权限、Trace 或持久化逻辑时必须确认：

- 是否使用了正确的 `conversationId`；
- 是否使用了唯一的 `requestId`；
- 是否会把事件串到当前激活会话；
- 同一会话是否可能启动两个 prompt；
- 后台会话是否仍可独立运行；
- 切换会话是否只改变 UI，不误停其他会话；
- 重试是否复用原始用户消息，避免重复追加用户消息；
- 中止后是否保留已生成内容和 Pi session 状态。

## 6. 工具、权限和沙盒规则

0.2.0 已交付主任务可靠性、统一执行接口、本机/Docker/Windows 原生预览及组合级压缩策略。已确认的维护/修复批次以开发 TODO 顶部状态为准；团队预算、上下文开放、协作增强和插件/工作流的具体开发范围仍需确认。

Pi 继续决定 Agent loop 和工具调用。Tao 可以做：

- 权限策略；
- 工具配置 UI；
- 自定义工具注册；
- 工具状态归约；
- 产品级审计；
- 现有执行后端的装配及后续扩展。

Tao 不应该：

- 根据用户问题猜测需要哪个工具；
- 再实现一个工具选择器；
- 再实现一套工具结果上下文；
- 用简单字符串替换冒充可靠 Shell 解析；
- 把权限确认叫成沙盒；
- 在没有隔离后端时宣称“不会损伤源文件”。

自定义工具增加执行方式时，必须同时考虑：

- 输入 Schema；
- 工作区和路径；
- 权限默认值；
- 超时；
- 错误脱敏；
- 测试调用和模型调用的区别；
- 是否允许网络；
- 是否进入发布资源。

## 7. 用户数据规则

- 用户数据统一在 `%USERPROFILE%\.tao`；
- 不把用户配置写入项目源码；
- 不把 API Key 放到 React 状态持久化、会话消息或发布资源；
- 不把 `.tao` 当工作区；
- 改数据格式时必须提供迁移；
- 改工作区字段时必须考虑跨电脑绝对路径失效；
- UI 只显示 API Key 是否配置，不显示明文。

## 8. UI 和产品边界

后续 UI 继续遵守：

- Tao 是产品名称，不在用户界面上暴露“Pi 产品目录”概念；
- 工作过程、Trace 和权限是产品级信息，不展示原始内部日志；
- 右侧面板保留可拖动宽度；
- 文件视图和工作过程视图不覆盖聊天内容；
- 主题必须覆盖聊天、设置、工作过程、文件预览和权限确认；
- 不用大面积临时弹窗堆叠复杂配置；
- 复杂配置优先使用独立页面、折叠区和可复用布局。

## 9. 文档和 TODO 规则

每轮讨论结束后先更新：

```text
docs/开发TODO.md
```

如果行为、路径、发布、数据或架构改变，同时更新：

```text
docs/项目手册/
```

文档中必须区分：

- 已经在代码中完成；
- 已经有接口但 UI 不完整；
- 只是设计目标；
- 当前明确不做。

## 10. 当前候选顺序与验收

文档收敛已完成。2026-10-22 用户确认先推进基础工具：联网 → Skills 可用性 → MCP → 文档与浏览器；搜索服务部署及分发可用性已明确暂缓。具体批次与验收以开发 TODO 为准。团队用量与预算治理、上下文/压缩可观察性、协作中断与共享写入可靠性，以及插件与确定性工作流保留为候选。候选顺序不等于具体功能已获开发授权。

主请求事件生命周期、多智能体基础、组合快照、压缩配置和工具沙盒已存在，不重复立项。后台未读与重启中断提示也已有基础，剩余是持久化决策、恢复交互与异常覆盖。

持续保持现有发布链路可用；按变更影响运行回归，得到出包确认后再编译并执行安装验收。干净电脑、Windows 10、原生卸载/重启/跨用户和多窗口异常等专项在 TODO 中独立追踪。静态检查、本地模拟、真实模型、用户整体试用及专项验收分别记录，不能互相替代。
