# Windows 原生沙盒：当前电脑验证

这是第一轮未准备系统兼容权限的历史记录。后续已实现最小兼容初始化与开发版预览，最新结果和限制见 [后端接入记录](./2026-10-20-Windows原生后端接入.md)。

日期：2026-10-20。范围：研究和独立原型；未接入产品默认后端，未构建 MSI 或推送发布。

## 结论

已完成当前电脑上的第一轮验证：**17 项用例，14 项通过、3 项兼容性失败，完整脚本返回码 1**。AppContainer + Job Object 可以完成基础隔离和进程回收，但当前 Git、NUL 设备和 Node 原生路径解析不兼容，暂不作为 Tao 的通用默认后端。

最低产品目标仍为 Windows 10 x64。用户目前没有 Windows 10 测试环境，已确认先完成当前电脑验证；本记录不代表 Windows 10 已通过验收。

## 实现机制

1. 每次执行创建一个唯一 `Tao.NativeProbe.<UUID>` AppContainer SID，不声明网络等能力。
2. 只向本轮测试目录授予该 SID 的读执行或读写权限。并发使用不同身份；ACL 修改通过命名互斥量串行合并，撤销时只移除本身份的项，不恢复整个旧 ACL 快照。
3. `CreateProcessW` 使用显式环境和标准句柄名单、`CREATE_NO_WINDOW` 及挂起启动；恢复前先加入 kill-on-close Job Object。
4. 控制器以 JSON 提供程序路径、参数数组、工作目录、授权目录、输入及超时；后续取消行或控制器输入 EOF 触发终止。输出保留 stdout/stderr 并限制大小。
5. 正常结束撤销临时授权并删除 profile；强杀 helper 后由外部清理日志恢复。日志重放是实验能力，尚未成为产品的启动恢复机制。

这是普通 AppContainer。它仍能访问 Windows 已向该类身份开放的系统公共资源，不能将本实验描述为完全虚拟化或严格只暴露几个目录的文件系统。实现依据为微软 [AppContainer 启动与双主体访问检查说明](https://learn.microsoft.com/en-us/windows/win32/secauthz/implementing-an-appcontainer) 和 [Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)。

|---|---|---|
| `node-workspace-read` | 通过 | 包内 Node 读取 `input.txt`，返回 `fixture 720` |
| `write-allowed-and-readonly-denied` | 通过 | 写授权目录成功，只读执行写入返回 `EPERM` |
| `outside-and-other-project-denied` | 通过 | 合成私有文件、另一个项目均返回 `EPERM` |
| `argv-stdin-unicode-and-clean-environment` | 通过 | 空参数、空格、引号、末尾反斜杠、中文和换行按数组保留；输入正确；未继承私有变量 |
| `child-inherits-appcontainer-token` | 通过 | Node 派生原生检查程序，实际令牌 `TokenIsAppContainer=true` |
| `powershell-command` | 通过 | Windows PowerShell 输出 `native-shell-ok` |
| `git-command` | **失败** | `git --version` 报 `/dev/null` 访问被拒绝，退出 128 |

| `node-native-realpath-compatibility` | **失败** | 已授权文件普通读取成功，但 `fs.realpathSync.native` 返回 `EPERM` |
| `network-denied-at-os-boundary` | 通过 | 宿主对照能连接本地 TCP 监听；沙盒连接未到达，匿名线程令牌连接也被拒绝（10013） |
| `concurrent-readonly-and-writable-identities` | 通过 | 两个唯一 SID 同时运行；可写方成功，只读方仍被拒绝 |
| `concurrent-project-read-grants-remain-separate` | 通过 | 并发两个项目互读均返回 `EPERM` |
| `junction-created-during-execution-does-not-expose-private-file` | 通过 | 启动后宿主创建指向合成私有目录的 junction；沙盒读取仍 `EPERM` |
| `process-tree-cancel` | 通过 | 真正派生子进程后取消，子 PID 消失，无延迟写入 |
| `process-tree-controller-eof` | 通过 | 关闭控制器输入模拟断连，子 PID 消失，无延迟写入 |
| `process-tree-kill-helper` | 通过 | 强杀 helper，Job 回收后代；清理日志仍在，外部清理完成 |

最后两项清理审计成功：本轮记录的 profile 已不在当前用户映射中，生成树的 ACL 中未残留本轮 SID。另行执行 `-CleanupOnly` 返回 0。

### 网络结论的范围

测试使用一个宿主回环 TCP 监听，分别运行宿主普通连接、宿主匿名线程令牌连接、AppContainer Node 连接及 AppContainer 匿名线程令牌连接。前两者可到达，后两者不可到达；还核对了监听端接入计数，避免只根据超时作判断。匿名探针在切换线程令牌前初始化 Winsock，探测 socket 在切换后创建。

这证明本次受控 TCP 场景中的边界，不代表公网、UDP、DNS、系统服务代连、任意代理和所有绕过手法均已认证。当前原型没有“允许指定域名”的网络代理，也没有联网执行模式。

### 进程与工具兼容性的范围

后代测试使用普通子进程和继承的标准句柄。早期尝试中，Node 自行新建管道的调用超时，`stdio: ignore` / 分离式启动又涉及 NUL 访问；因此不能将目前通过的继承句柄测试视为任意管道、后台服务或第三方工具均可用。

测试改用明确授权的包内 Node 副本后，实际子进程和四项回收用例才完整执行。没有通过“子进程根本未启动”来计算回收通过。尚未覆盖完整桌面异常退出、断电后的自动恢复、资源压力与真实项目长期运行。

## 三项失败如何解释

### Git 和 NUL

原生对照排除了“只是 Git 参数或 Node 路径错误”：同一个 Win32 打开设备操作在宿主成功，在 AppContainer 得到访问拒绝。微软的 [MXC 宿主准备文档](https://github.com/microsoft/mxc/blob/main/docs/backends/process-container/host-prep.md) 也说明旧兼容层存在系统根目录元数据和 Null 设备授权准备；Null 设备的权限准备还可能需要每次重启重新应用。

本次没有运行这些系统级准备，没有改系统设备或磁盘根目录的 ACL。该文档提供了排查方向，不等于适合 Tao 直接照搬，更不代表已有的一次安装即可解决全部兼容问题。

### Node 原生路径解析

包内 Node 22.19.0 对同一文件普通读取成功，但原生 realpath 失败。这是实测兼容性阻碍。微软仓库的 [路径解析问题记录](https://github.com/microsoft/mxc/issues/694) 提供了 AppContainer 与 DOS 设备命名空间的相关线索；这里将其作为解释候选，未声称已独立定位 Windows 内部的全部原因或证明修复有效。

Tao 会使用 SDK 和大量文件工具，只验证 `node -e` 启动不足以判断可发布。

## 与现有方案的关系

| 方案 | 对 Tao 的判断 |
|---|---|
| 本轮 AppContainer 原型 | 无需 Docker，基础边界可验证；存在三项真实兼容失败，保留为实验 |
| Codex 传统 Windows 路径 | 可借鉴受限身份、文件授权、网络策略和初始化分离；需要继续验证工具兼容及令牌变化时的边界 |
| Codex MXC 路径 | [官方适配说明](https://github.com/openai/codex/blob/014489466a1739c2c563cdfe57880c2c7c8680e3/codex-rs/mxc-sandbox/README.md) 要求可用的原生进程隔离能力，不能把旧 AppContainer 回退当成同一后端的兼容保证 |
| Anthropic sandbox-runtime Windows alpha | [官方项目](https://github.com/anthropics/sandbox-runtime/tree/c40cf14a65d025e3cd27f071f13a73c12b3b1f92#windows-alpha) 有专用账户、受限令牌、ACL 和 WFP 方案；已列明兼容及安全限制，不能直接视为 Tao 已可用的组件。本次未安装或运行它 |
| Docker 后端 | 保留当前可选实现；用户未安装 Docker 时，不能将其作为原生隔离的隐式替代或静默回退本机 |

对照来源核查于 2026-10-20；第三方实现及支持范围会变化。Windows API 存在于较旧系统，不等于当前实现已在所有 Windows 10 版本上通过。

## 下一批建议和验收门槛

1. 优先继续对照“专用受限身份 + ACL + 网络策略 + Job Object”的 Windows 10 候选；将可信宿主、初始化程序和沙盒工具进程分开。先验证 Node 文件工具、Git、PowerShell、子进程管道及匿名 / 派生令牌网络行为，再决定实现路线。
2. 若继续 AppContainer 路线，单独评估系统准备的最小授权、重启恢复、卸载回收和对其他应用的影响；不能为得到通过结果直接扩大系统访问。两条路线均以工具兼容性和真实边界为判断标准。
3. 正式接口需要区分不可用 / 初始化未完成 / 策略不支持 / 工具不兼容；初始化失败或策略无法保证时拒绝执行，禁止静默降级。
4. 补齐执行租约、启动恢复、权限日志归属校验，以及多会话不同授权的并发回归。定义 CPU / 总内存预算后再做压力验收。
5. 有条件后补 Windows 10 x64 真机或虚拟机，记录准确版本、标准用户及管理员初始化路径；再进入 Runtime、配置 UI、MSI 资源与安装升级验收。

本批交付到调研和当前电脑原型验证为止；现有 Runtime 和默认执行后端未切换。其余权限、Docker 和压缩策略源码仍按前一批独立验收记录追踪。
